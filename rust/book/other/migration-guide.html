Edomata for Rust

Migration guide for Scala and Java users

This guide is for teams who know the Scala library (or its Java API) and want to use, or move to, the Rust port. The port keeps the semantics, invariants and on-disk formats, so a migration can be gradual: Rust and Scala services can run side by side on the same database.

Sharing a database

Nothing changes on disk:

  • Tables and DDL are byte-for-byte identical (PGSchema, SaaSPGSchema), for both naming strategies (PGNaming::schema = "ns".journal, PGNaming::prefixed = ns_journal) and every payload type. Golden tests compare the Rust output with files generated by the Scala code.
  • Queries match the Skunk / Doobie Queries.scala: same columns, ordering, on conflict upserts, unique-violation handling (23505 → VersionConflict).
  • Payloads default to jsonb, written in the native PostgreSQL binary format like the Scala codecs. JSON written by Circe, jsoniter (including jsoniter’s msgpack, which writes JSON bytes) and uPickle’s JSON codec is readable by edomata-serde, provided your Rust types serialize to the same JSON shape (see below).
  • Snapshots, commands, migrations use the same tables, so a Rust process resumes where a Scala one stopped. The cross-language test (rust/crates/edomata-e2e/tests/cross_language.rs) has Scala write events, commands, outbox items and a snapshot, Rust read them and append, and Scala verify the result.

Matching the JSON shape

Circe’s generic derivation of Scala 3 enums encodes a case as {"CaseName": {fields}}, including parameterless cases ({"Opened": {}}). In serde, use struct variants everywhere (Opened {}) so that the externally-tagged encoding matches, and #[serde(rename_all_fields = "camelCase")] (or per-field rename) for camelCase field names. BigDecimal fields are JSON numbers: rust_decimal::Decimal with rust_decimal::serde::float reads and writes them. edomata_serde::compat::upickle_option handles uPickle’s Option encoding. The edomata-e2e crate is a worked example against the Scala accounts domain.

Known limitation: uPickle msgpack

Payloads written by uPickle’s msgpack codec (real MessagePack in bytea columns) cannot be read by the Rust port, because serde_json is the only serializer. Migrate such journals to JSON with an event migration before sharing them with Rust, or keep them on the Scala side.

Behavioural differences are recorded in the ADRs; the main ones: programs have no error channel (a failing effect is a panic or a BackendError from the storage, ADR 0005); Cats’ Traverse instance of ResponseT is not ported (no Traverse in Rust, ADR 0004; Decision keeps its traverse laws, as FromIterator and transpose); Response, the deprecated Scala alias, is not ported.

What is new in Rust

  • Broker distribution: OutboxRelay / JournalRelay with Kafka and RabbitMQ publishers, leader election and at-least-once delivery with stable ids (Distributing events).
  • Cross-process wake-ups: with_outbox_notify_channel / with_journal_notify_channel on the drivers plus edomata_broker::postgres::listen.
  • In-memory driver reproducing the PostgreSQL constraints, for tests and prototypes.
  • DDL under an advisory lock when several replicas create tables at once.
  • wasm32 support for edomata-core (built in CI).

Step by step

  1. Point a Rust service at the existing database with the same namespace and naming strategy (schema unless you used PGNamespace.prefixed; Java API users are on prefixed naming, which SimpleBackend::builder(..).namespace(..) also uses).
  2. Define your event, state and notification types with serde derives matching the stored JSON; verify with a small program that reads the journal (backend.journal().read_all().try_collect(), a stream).
  3. Run the Rust and Scala services side by side; they share the commands table, so a command handled by one is redundant for the other.
  4. Move processes (outbox consumers, projections) over; OutboxConsumer marks items exactly like Scala’s.
  5. Retire the Scala service.
